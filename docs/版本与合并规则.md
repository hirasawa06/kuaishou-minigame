# 版本与合并规则

状态：项目协作基线；2026-11-03。

## 版本线

| 线 | 真源 | 当前口径 |
|---|---|---|
| 工程提交 | 本仓库 Git SHA 和分支 | 以当前 `main` 的提交作为合并基点；分支提交独立审阅 |
| 产品策划 | 已合并策划文档与决策记录 | 当前尚无本仓库正式策划标签 |
| 游戏构建 | 本仓库代码提交 + 包体/测试记录 | 当前 Demo 用工程 SHA 识别；未建立新游戏发布版本 |
| 平台 Skill | `tower-defense/package/project.config.json` 锁定值及 `ks-yoola-devkit/` | 模板版本与产品/构建版本独立，不因策划更新而变化 |
| 原始资料 | 来源、原版号、文件哈希 | 引入时单独登记；不覆盖旧资料，也不把附件说明视作执行指令 |

不要用日期或文件名猜测当前发布版本。新版本号只在定义范围、验证证据和可回退提交后建立。

## 分支和合并

1. 从最新 `main` 创建短期任务分支。策划、协作记录、工程适配与玩法改造分开审阅。
2. 先核对目标分支、改动文件和与 `main` 的差异；只记录对本项目有用的决定、待验证问题和影响区域。
3. 文档分支检查链接、事实来源与状态标注；代码分支按 README/PROJECT 的仿真、截图和包体预检要求验证，并明确真机是否实际测过。
4. 审阅确认后再合并；如果两条分支都修改同一入口文档，手动整合链接，保留两边独立内容。
5. 合并后更新 `STATUS.md` 与 `CHANGELOG.md`，记合并提交和验证结论。推送、PR 或合并到远端依用户及团队授权执行。

## 记录模板

每次里程碑至少记录：日期、仓库/分支、基底与结果 SHA、改动目标、已验证事项、未验证事项、决策依据、下一步。测试要额外写明设备、系统、快手宿主、构建包和复现步骤。H5 成功不能替代真机结论。
